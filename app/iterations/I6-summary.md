# I6 · 切图外溢修复 + 上下瀑布流

> 起点：用户反馈两件事 ——「切图还是有问题，又出现了错位的现象，还把原文一起给切过来了」、
> 「能不能做成上下瀑布流翻页啊。这样好麻烦」。

---

## 1. 「把原文一起切过来」的根因：跨栏裁切范围外溢到了别的栏

### 怎么定位的

没有靠猜，而是先加了一个**量化指标** `stats.duplicatedTextArea`：

> 正文块的面积被图像切片覆盖了多少。不为 0 就意味着同一段正文会在页面上**出现两次** ——
> 一次是重排后的 HTML 文本，一次是切片图像里的像素。

跑离线校验，问题立刻现形：

| 页 | 重复块数 | 重复面积 |
|---|---|---|
| 第 4 页 | **7** | **222950 px²** |
| 第 5 页 | 1 | 3930 px² |
| 其余 | 0 | 0 |

再把那 7 个块打出来，全是右栏正文：

```
⚠ 重复 [×1.00] x=463→818 y=108→340 :: Residual Network. Based on the above plain
⚠ 重复 [×1.10] x=463→604 y=350→369 :: 3.4. Implementation
⚠ 重复 [×1.00] x=463→818 y=379→629 :: Our implementation for ImageNet follows th
⚠ 重复 [×1.10] x=463→659 y=763→782 :: 4.1. ImageNet Classification
...
```

### 根因

第 4 页的架构图 **x 只到 427，而栏缝在 414** —— 它只超出栏缝 **13px**，
就被 `coveredColumnIndexes` 判为「跨栏元素」，于是裁切范围被扩到**整幅版心**（75→818），
把右栏那些正文全切了进去。

这是 I4 那次修复的过度反应：当时为了让「同条带内、簇范围之外的图形」也被覆盖，
把跨栏图形的裁切范围一路扩到了整幅版心。

**三版裁切范围的对比** —— 两个极端都试过，最后取中间：

| 裁切范围 | 后果 |
|---|---|
| 簇自身的窄包围盒 | 同带内的其他图形失去覆盖（第 4 页 33 → 229 条未覆盖） |
| **整幅版心** | **把别的栏的正文切进来，同一段文字出现两次** ← 用户看到的 |
| **该纵向带内全部图形路径的并集** ✅ | 既覆盖同带图形，又不外溢 |

### 顺带修掉的第二个问题：跨栏图形吞掉非归属栏的正文

排查中发现另一个更隐蔽的缺陷：跨栏障碍**出现在每一栏的排布里**，非归属栏生成 `skip` 片段，
把该栏整个 y 区间吞掉。第 4 页的跨栏图形 y 146→926，右栏 4 段正文（y 379/630/763/792）
全落在它之后，被 `skip` 一并吃掉 —— **正文凭空消失**。

修法是区分两类跨栏元素（`isSpanningFigure` 标记）：

| 类型 | 非归属栏的处理 | 理由 |
|---|---|---|
| 跨栏**正文块**（横跨两栏的标题） | 保留 skip | 它在本栏的像素也属于自己（标题右半就在右栏） |
| 跨栏**图形** | 不参与排布 | 裁切范围已限于图形并集、不覆盖别的栏 |

### 结果

| | 修复前 | 修复后 |
|---|---|---|
| 第 4 页重复块 | 7 个 / 222950px² | **0** |
| 第 5 页重复块 | 1 个 / 3930px² | 1 个 / 3930px²（待查） |
| 第 4 页未覆盖图形路径 | 3 条 | **3 条**（未恶化） |

新增 3 个单测：略超栏缝不外溢、跨栏障碍不吞非归属栏正文、并集裁切。

## 2. 上下瀑布流：连续滚动阅读

原来的形态是「一页一页看」——要点「下一页」，还要等它重新解析、重新渲染。
12 页的论文就要点 11 次，这正是用户说的「好麻烦」。

改成**连续滚动**：所有页面依次排列，向下滚动即可连续阅读。

### 设计取舍

**为什么按顺序加载，而不是全部并发**

每页都要一份离屏画布（918×1188 @dpr2 ≈ 17MB）+ 若干切片画布。
十几页同时渲染会瞬间吃掉几百 MB。而用户本来就是自上而下读的，
所以第 N 页就绪才放开第 N+1 页 —— 加载节奏天然匹配阅读节奏。

**状态收进组件，而不是堆在 App 里**

每页都需要**自己的一份**离屏画布、图形路径、跨栏区域与译文映射。
放在 App 里就得维护 `analysis1`、`analysis2`… 或一个 map 加一堆空值判断。
抽成 `PageFlowBlock` 组件后这些状态天然按页隔离。

**跳页**

「上一页 / 下一页」按钮保留，但语义变成**滚动定位**（并放开目标页的加载）。
页与页之间用一条虚线 + 居中的页码分隔 —— 连续滚动下，「页」这个概念需要一个最小提示，
否则读者不知道自己在第几页。

### 踩到的两个坑

1. **切换缩放没有重新渲染**。组件内部对同一页只加载一次（有意为之，避免重复解析），
   于是切到 150%/200% 时内容高完全不变。修法是给 `key` 带上 scale 强制重建，
   同时把加载进度收回到当前页 —— 否则已解析的每一页会同时重渲染。
2. **截图脚本滚不动**。滚动容器是 `main.viewport`（有独立 overflow），**不是 window**，
   对 window 调 `scrollTo` 毫无效果。已修正并记在脚本注释里。

## 4. 关于 OCR：不解决当前问题

用户提议「换个技术路径使用 OCR」。**这里需要澄清一个前提**：

当前的问题**不是「文字识别不出来」**，而是「哪些像素属于正文、哪些属于图形」的**分割**问题。
OCR 做的是「图像 → 文字」，它同样要先做版面分析才能区分正文与图表 ——
**问题会原封不动地留在同一层**，而且 OCR 还会引入识别错误（文本层是 100% 准确的）。

OCR 的真正位置是**降级路径**：扫描版 PDF（整页位图）根本没有文本层。
但那是另一个场景，本轮顺手加了探测：

> 本页没有文本层 —— 可能是扫描版 PDF。当前版本不支持 OCR，只能以原版式查看。

**静默失败比不支持更糟** —— 否则用户打开扫描版论文只会看到空白页面，猜不出原因。

OCR 应排在接入真实翻译、侧边栏持久化之后，并走 `docs/03-data-flows.md` 里
已预留的 ParserSidecar 降级路径（Python 子进程，故障隔离）。
