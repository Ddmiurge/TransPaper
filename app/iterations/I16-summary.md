# I16 小结 · 公式检测补盲（修「部分公式仍被翻译」）

> 迭代日期：2026-09-26 · 样本：two-column / single-column / acl（三基线）
> 触发：用户实测反馈「仍然有部分公式被拿去进行翻译了」。经确认是**独立成行的公式**
> （display equation）被漏检，而非行内公式（行内公式属另一类问题，见末尾「已知限制」）。

## 目标

ADR-013（I10）把行间公式做成图像切片、不翻译，但判据有两类漏检，导致真实论文里仍有公式
被整段送去翻译。本迭代把漏检堵上，并加一条三基线的回归守护。

## 查到的根因（两处，都是真实论文里会遇到的形态）

1. **极简无编号等式**：`a = b + c` 这类符号密度仅约 0.33，低于旧判据 `mathDensity ≥ 0.4`
   的硬门槛，于是留在可译集合里被翻译。
2. **带描述性标识符的编号公式**：ACL 第 3 页的
   `min Lret + λ1 · Lsemantic + λ2 · Lperceptual (2)` 与
   `∆reason(madv) = EQ[1[Gadv ∈ Agent(Q, M)] − 1[…]] (4)` 是真正的公式，却仍被翻译。
   原因：它们有大量 ≥3 字母的标识符（Lsemantic / Agent / madv），既把 `longWords` 推过
   `≤2` 的门槛，又把数学密度稀释到 0.18 以下 —— 旧判据两头都不满足，直接放行。
   这条是**新加的基线泄漏守护测试**在 acl p3 抓出来的（之前三基线扫描没覆盖到）。

## 修复（`src/domain/formulas.ts`）

- 新增 `strongDensity`：**数学符号密度去掉单纯的圆括号**。因为 `Eq. (1)` / `see Figure 3 (1).`
  这类只是「以编号结尾的正文」没有强运算符（= + − × ÷ ≈ ≤ ≥ ∈ λ…），靠它挡住误判。
- **编号分支**：把 `mathDensity ≥ 0.18 && longWords ≤ 2` 换成 `strongDensity ≥ 0.1`。
  真正区分「公式」与「以 (N) 结尾的句子」的是**强运算符密度**：公式里 = + − ∈ λ 密布，
  而句子里一个都没有。描述性标识符不再误伤。
- **无编号分支**：`longWords === 0` 仍是强防线（正文句子必有 ≥3 字母词），但把单行门槛从
  `mathDensity ≥ 0.4` 降到 `strongDensity ≥ 0.3`（兜住 `a = b + c`），并新增**多行路径**
  `strongDensity ≥ 0.25`——覆盖 align 环境被拆成多行、且首行没被认出的情形。
- 早期返回 `lineIds.length > 3` 放宽到 `> 8`，让被拆成多行的整段公式仍有机会被认出。

## 已知限制

- **行内公式（嵌在句子里，如 `…where f(x) = y…`）仍会跟着整段正文被翻译**——这属于另一类
  问题：当前架构把整段正文作为一个翻译单元，行内数学没有被单独抽出来。本次按用户确认只处理
  「独立成行的公式」。若日后要彻底消灭行内公式翻译，需要把块内行内数学 span 拆成
  独立不译单元（改动翻译/分段模型），可作为单独迭代。
- 编号公式的强运算符门槛 0.1 是 ACL + ResNet 两个样本标定的；个别极简、几乎无运算符的
  编号公式（如裸 `x (1)`）仍可能漏——但这类极少见。
