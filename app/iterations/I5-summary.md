## 1. 核心发现：矩阵累乘方向反了（一个伪装成「算法不好」的 bug）

### 症状

用「图形路径应当覆盖图内文字」做交叉验证。图内文字的坐标取自 pdf.js 的文本变换，
与路径提取是**两条独立的代码路径**，前者已在多轮迭代中被反复验证可靠 —— 所以它能当基准。

| 页 | 吻合率 |
|---|---|
| 第 1 页 | **0%** ❌ |
| 第 2 页 | 40% ❌ |
| 第 6 页 | **0%** ❌ |
| 第 4 页 | 84% ✅ |
| 第 5 页 | 69% 🟡 |

第 1 页的对照最清楚：图 1 的图内文字在视口 `(474–807, 341–400)`，
路径却算在 `(339–693, 534–651)` —— 完全不重叠。

### 排查过程（走过两条死路，值得记下来）

1. **先怀疑 form XObject 的 BBox 平移**。读 pdf.js 源码确认：当前版本里 BBox 只用于
   `clip()`，**不做平移**（旧版本做过）。假设排除。
2. **再怀疑位图图像**。统计各页的 `paintImageXObject` —— 全 0 个，本 PDF 的图全是矢量。排除。
3. **最后靠手算矩阵定位**。把第 1 页的 `ctm` 在关键算子处逐个打印：

   ```
   312 transform [1,0,0,1,308.9,489.3]      → ctm = [1,0,0,1,308.9,489.3]
   314 transform [0.73143,0,0,0.73143,0,0]  → ctm = [0.73,0,0,0.73,225.9,357.9]
   321 constructPath  minMax=(0,0.4)-(172,107.1)
   ```

   代码算出图的原点在 `(225.9, 357.9)`，但按 PDF 语义应该是 `(308.9, 489.3)`
   —— 正好是**平移量本身**，没有被缩放乘掉。

**根因**：PDF 的 `cm` 语义是 `CTM_new = M × CTM_old`（**左乘**），
而代码写成了 `multiply(ctm, args)`（右乘）。

### 为什么它能潜伏这么久

**单一变换时两种写法结果相同**（`I × M === M × I`）。
第 4、5 页的图形变换结构简单，看起来一切正常；只有第 1、6 页那种
「平移叠缩放叠 form 矩阵」的多层嵌套才暴露偏差。

换句话说：它伪装成了「第 1、6 页的图形检测算法不好」。
如果只用肉眼看截图验收，会去调图形检测的阈值 —— 而那个方向永远调不好。

### 修复与验证

```ts
// operatorPaths.ts
ctm = multiply(args as number[], ctm);   // 曾误写为 multiply(ctm, args)
```

| 页 | 修复前 | 修复后 |
|---|---|---|
| 第 1 页 | 0% | **84%** |
| 第 2 页 | 40% | **100%** |
| 第 6 页 | 0% | **100%** |

修复后第 1 页的图形判定质量（离线校验实测）：

```
[图像:font-size] ×0.33 :: 20 20
[图像:font-size] ×0.66 :: 56-layer
[图像:font-size] ×0.66 :: test error (%) training error (%)
[图像:font-size] ×0.33 :: 0 0 1 2 3 4 5 6 00 1 2 3 4 5 6
[正文] ×0.90 :: Figure 1. Training error (left) an…
```

图 1 的轴标签全部归入图像区域，而图注正确保留为可译正文。

**防回归**：新增 `src/pdf/__tests__/operatorPaths.test.ts`（8 个用例），
核心是「平移后再缩放」这个最小复现 —— 右乘会得到差一个缩放倍率的结果。
这个文件还守住了 save/restore 配对、视口变换、非有限值容错。

## 2. 纯留白不该被切成图像

### 症状

第 1 页 9 个图像切片里 **7 个是纯白的**。它们对应标题与作者之间、
作者与 Abstract 之间的版式留白。页面上因此出现莫名的大段空白，
「段间距交给 CSS」这个设计意图完全落空。

### 为什么原有的像素判据拦不住

`hasContent`（判断裁切区里有没有墨迹）本应挡住它们，但实测全部返回 true。
原因：空隙的下沿**紧贴文本块的包围盒**，而包围盒底边还含一点字形余量
（`bbox.height = fontSize × 1.15`），于是采样到的「墨」其实来自相邻的文字。

### 改法

用**几何判据**替代像素判据：空隙里存在图形路径（同时看 x 与 y）才切成图像。

```ts
const gapHasFigure = (y0: number, y1: number) =>
  !hasFigureInfo ||
  figurePaths.some(
    (p) => p.y + p.height > y0 + 0.5 && p.y < y1 - 0.5 && p.x + p.width > left && p.x < right
  );
```

副作用是它变得可以在 Node 里离线测试 —— 这正是 `hasContent` 做不到的。

### 一个反直觉的坑（单测抓到的）

**把 image 片段「删掉」是没用的。** 正文片段结束后会 `startRun`，
若这里不留断点，这个 run 会一路延续到下一个正文片段，把留白又切了进去。
必须压成一个 `skip` 片段来切断它。

第一次改完跑单测：切片数量纹丝不动 —— 才发现这个机制。

### 效果

| | 修复前 | 修复后 |
|---|---|---|
| 第 1 页图像切片 | 9 | **3** |
| 其中全白 | 7 | **1** |
| 页面高度（100%） | 3339px | **2999px** |

离线校验（`droppedGapHeight` / `coveredHeight`）：第 1 页省掉 304px 留白，切图 162px。

## 3. 旋转文字必须排除在文本流之外

### 症状

```
arXiv:1512.03385v1 [cs.CV] 10 Dec 2015Deep convolutional neural networks [22, 21] have led
```

arXiv 的竖排侧标与正文粘成了一句。更糟的是该块字号是正文的 1.5 倍，
于是被判为**二级标题** —— 侧标成了正文里的大字标题，顺带吞掉了紧跟的正文。

### 关键点：必须在成行之前剔除

`groupIntoLines` 用基线聚类。旋转文字的基线与相邻正文行相近，
**一旦被并进同一行，后面无论怎么判都会连带出错** —— 所以不能等到判定阶段再标记。

### 判据

水平排布的变换矩阵形如 `[fs, 0, 0, fs, x, y]`，第二三分量恒为 0。
旋转/斜切会让它们非零，量级与字号同阶。实测取值只有
**0 与 ±fontSize 两种极端**，所以 5% 的相对阈值很宽裕。

斜体不受影响 —— PDF 的斜体是**字体**属性，不进矩阵。

判据放在 `domain/geometry.ts`（域层），**测试与生产共用同一份** ——
各写一份迟早会漂移，届时测试通过而线上错误。

剔除后它们所在的区域交给图像切片覆盖，符合「非文本内容保持原样」。

### 效果

- 第 1 页旋转文字 3 项（2 个轴标签 + 1 个侧标），泄漏进文本流 **0 项**
- 可选中段落 15 → **14**（假标题消失）
- 页面高度再降 46px

## 6. 这一轮真正学到的东西

**「部分场景正确」是最难查的 bug 类型。**

矩阵方向反了之后，4 页正常、2 页错得离谱。如果抽样只看那一两页正常的，
会得出「已经好了」的结论；如果只看错的那两页，会去找一个根本不存在的
「第 1 页特殊结构」。

真正的突破口是**换一个独立的信号做交叉验证**：路径来自 `constructPath` 的 minMax，
文字来自 `textTransform`，两者无关，但物理上必须吻合。这个判据一旦建立，
问题立刻从「可能是算法不好」变成「坐标系统性偏移了多少」。

**同类判据在本项目里已经出现过两次**（栏检测的覆盖率计数法、图形夹住判据），
**这是第三次**。应当把它固化为习惯：任何「从 PDF 提取的几何量」都要有一个
来自不同代码路径的交叉基准。

**另一个反复出现的模式：像素判据不可靠，几何判据可靠。**
- 图形区域检测：像素采样（随缩放漂移）→ 矢量路径 ✅
- 空隙内容判定：像素采样（被相邻文字触发）→ figurePaths 相交 ✅
- 坐标可信度：用像素（路径框里有没有墨迹）只是**兜底自检**，不是主判据

**核心几何计算必须可离线测试。** 本轮新增的两个测试文件都是纯函数，
不需要浏览器 —— 修复当天就靠它们各抓到一次自己的错误。
