# ADR-007: 采用 SQLite 作为主存储

## Status

Accepted（2026-09-20）

## Context

本项目的存储需求有四个特征，缺一不可：

**① 数据规模**。一篇 100 页论文约产生 1500 - 3000 个 Block、250 - 400 个 Segment。用户积累 500 篇论文时，Block 表达到百万行量级。

**② 查询形态是跨实体、带条件、需要 join 的**。典型查询：

```sql
-- 「2023 年之后、打过 GNN 标签、且正文提到 attention 的论文」
SELECT DISTINCT p.id, p.title
FROM paper p
JOIN paper_tag pt  ON pt.paper_id = p.id
JOIN tag t         ON t.id = pt.tag_id
JOIN document d    ON d.paper_id = p.id
JOIN segment s     ON s.document_id = d.id
JOIN segment_fts f ON f.rowid = s.rowid
WHERE p.year >= 2023 AND t.name = 'GNN' AND segment_fts MATCH 'attention';
```

这不是偶发查询——侧边栏的集合筛选、标签筛选、搜索框都会产生这类查询。

**③ 高频小事务**。翻译过程中每完成一段就要落库一次，一篇论文 250 - 400 次写操作，且必须支持"部分失败后重试"。

**④ 内置全文检索需求**。侧边栏的「管理」需求必然包含搜索，而用户要搜的不只是标题，而是"**正文里提到 attention 的论文**"。

候选方案：

| 方案 | ① 规模 | ② 查询 | ③ 事务 | ④ 全文检索 | 零运维 |
|---|---|---|---|---|---|
| 文件夹 + JSON | 差（全量扫描） | ❌ | ❌ | ❌ 需自研 | ✅ |
| IndexedDB | 可 | ⚠️ 无 join | ⚠️ | ⚠️ 弱 | ✅ |
| LMDB / RocksDB / sled | 优 | ❌ 仅 KV | ✅ | ❌ 需自研 | ✅ |
| **SQLite** | ✅ | ✅ | ✅ | ✅ FTS5 | ✅ |
| PostgreSQL / MySQL | ✅ | ✅ | ✅ | ✅ | ❌ 需装服务 |

**"文件夹 + JSON" 的三个致命问题**（这是最直觉的方案，必须说明为什么不选）：

1. 跨论文查询要打开并解析 500 个 JSON 文件，无法优化
2. 改一个 Block 的 `translatable` 标志要重写整个 `blocks.json`（数 MB）。而翻译**每完成一段就要落库一次**，这个代价直接变成灾难
3. 翻译一批 20 段、失败 5 段，没有任何回滚机制

**PostgreSQL 的问题**：能力全都够，但要求用户为了一个单机阅读器额外安装并维护一个数据库服务。并发、网络访问、高级特性在单用户场景**一条都用不上**。

## Decision

**采用 SQLite 作为唯一的结构化数据存储**，配合文件系统存放二进制资源。

关键配置与约束：

1. **WAL 模式**：`PRAGMA journal_mode = WAL`，提供"多读单写"并发
2. **严格划分存储边界**：数据库**不存大 BLOB**。PDF 原文件、缩略图、图表裁剪图存文件系统（AssetStore，内容寻址），数据库只存内容哈希
3. **单写者模型**：所有写操作经**唯一的写队列**串行化，由专用线程持有唯一写连接；读操作使用独立连接池
4. **FTS5 全文检索**：`paper_fts` 检索元数据，`segment_fts` 检索正文，使用 `trigram` tokenizer 以支持中文
5. **迁移用 `PRAGMA user_version`** + 有序 SQL 文件，迁移失败则拒绝启动

完整 DDL 见 `04-storage-design.md`。

## Consequences

### 变得更容易

- **零运维**。SQLite 是嵌入式库，链接进进程。用户安装完应用即可使用，不需要任何额外步骤。这是桌面软件的关键约束。
- **数据是文件，不是服务**。整个文献库就是 `library.db` + `assets/` 两项。备份 = 复制；迁移设备 = 拷走；用户能理解、能控制。对"个人长期知识积累"这类数据，用户对数据位置的掌控感是产品信任度的一部分。
- **一条 SQL 解决的跨论文查询**。上文那个 join + 全文检索的查询，在 JSON 方案里需要全量扫描。
- **FTS5 是决定性优势**。它提供三样东西：`bm25()` 相关性排序、`snippet()` 生成命中片段、`highlight()` 生成高亮标记。侧边栏"标题 + 高亮摘要"的 UI，用一条 SQL 就能拿到。若用 KV 存储（LMDB / RocksDB），全文检索需要自研——这是重新发明轮子。**这一条是把 SQLite 与嵌入式 KV 存储区分开的关键因素。**
- **真正的事务与崩溃安全**。翻译 20 段是一个事务；进程被 kill 后重启，数据一致。JSON 方案做不到。
- **局部更新**。改一个 Block 的字段是 `UPDATE` 一行，不是重写整个文件。
- **WAL 的读写并发**。UI 线程读文献列表的同时，后台翻译线程在写译文，互不阻塞。这对"一边翻译一边浏览"是刚需。

### 变得更困难 / 需要接受

- **单写者模型带来架构约束**。WAL 提供的是"多读单写"，不是多写。因此**必须有一个全局写队列**，不能有第二个写连接。违反的后果是 `SQLITE_BUSY` 与延迟尖刺。这不是可选的优化，是必须遵守的约束。
- **中文分词需要额外配置**。FTS5 默认的 `unicode61` 对中文按字切分，检索效果很差。必须用 `trigram` tokenizer。代价是**索引体积增至原文的 3-5 倍**，且查询串长度需 ≥ 3 字符。这个坑不做中文检索不会暴露。
- **库文件不能放网盘同步**。iCloud / Dropbox / OneDrive 两端同时修改 SQLite 文件会导致冲突甚至损坏。这是真实痛点（用户可能想多设备使用），但无法通过技术手段完全解决。**必须在 UI 中明确警告**，二期考虑导出 / 导入合并或 CRDT。
- **百万行需要索引设计**。SQLite 能处理 TB 级数据，但前提是查询走索引。`block(document_id, read_order)` 与 `segment(document_id, read_order)` 这类复合索引是必须的，不是优化项。
- **需要避免大 BLOB**。若把 PDF 和图片存进 BLOB 字段，库文件膨胀到 GB 级，备份变慢、`VACUUM` 痛苦。因此存储边界（见 `04` §2）是硬性规定而非建议。

### 明确放弃的东西

- **不做多设备实时同步**。见上面的网盘限制。
- **不引入 ORM**。SQL 已经足够简单，ORM 会隐藏掉本项目需要精确控制的索引使用与事务行为。
- **不做数据库加密（MVP 阶段）**。SQLCipher 会引入额外的构建复杂度与性能开销。若后续有需求（处理涉密文献的用户），可作为可选特性引入——因为存储层已被端口隔离，替换适配器不影响领域层。
- **不做向量检索（MVP 阶段）**。二期用 `sqlite-vec` 在同一库内实现，避免引入第二个存储系统。

### 何时应当推翻此决策

如果出现以下任一情况，说明 SQLite 不再适用：

1. 需要多设备实时同步成为**核心需求**（而非附加需求）→ 需要客户端-服务端架构
2. 需要在同一文献库上支持**多用户并发写入** → 需要真正的数据库服务
3. 单库超过数 GB 且查询延迟可见 → 需要重新评估数据模型（可能是不该把 Block 全量持久化）

在此之前，SQLite 的收益远大于其限制。这四条约束——零运维嵌入式、单文件可备份可迁移、完整关系查询、内置全文检索——能被单一方案同时满足的选项几乎没有。
