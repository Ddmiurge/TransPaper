# ADR-010: 重排输出的排版规则

## Status

Accepted（2026-09-22）

## Context

ADR-008 把渲染方案定为"正文抽成 HTML 文本 + 图形保留为图像"，但没有规定**这份 HTML 该怎么排**。第一版实现只关心"内容正确"，样式上做了两个顺手的选择：

1. 译文用**带色块的框**呈现（浅青底 + 左侧色条），因为"这样一眼能看出哪段是译文"
2. 正文铺满页面内容宽度（150% 缩放下 743px），字号 16.8px

用户看到成品后的反馈是明确的：

> 「我希望的效果是能像 latex 一段原文，一段译文编译出来的模样。你这个下面一段绿色的框非常难看。而且重排的那些段落不像是正常的段，没有排版（比如首行缩进）。」

这两条都不是审美偏好问题，而是**可诊断的排版缺陷**：

**色块为什么是错的。** 它把连续的阅读流切成一节一节的方块，读者每读一段都要重新定位边界。而中英对照真正需要的只是"一眼分清哪段是译文"——字色就能做到，代价却小得多。

**行宽为什么是错的。** 双栏论文两栏合一后行宽变成原来的两倍。150% 下内容宽 743px、字号 16.8px，即一行 44em（约 88 个西文字符）。这远超舒适阅读区间（书籍常规 30–40em），回行困难，读起来就是"文字墙"——这正是"不像正常段落"的主要来源，而首行缩进的缺失只是次要原因。

## Decision

**以"印刷体文档"而非"网页卡片"作为重排输出的设计目标。** 具体五条：

### 1. 不用框，用字色区分译文

- 原文：`--read-ink`（近黑 `#15181d`）
- 译文：`--read-trans`（沉稳蓝灰 `#31536e`）
- 无背景色、无边框、无圆角

"一对"的绑定关系改由**间距**承担：译文紧跟它的原文（`margin-top: 0.45em`），换到下一组时拉开（`margin-bottom: 1.5em`）。间距承担原先色块的作用，而不打断阅读流。

### 2. 行宽（measure）必须约束在 36em

```
measure = min(内容宽, 36em × 基准字号)
```

36em 约合 72 个西文字符或 36 个汉字，落在书籍排版的常规区间。

**图像切片等比缩到 measure 内**（`sliceScale = measure / 内容宽`），与 LaTeX 把图缩放到版心宽度同理。字号放大时 measure 同步放大，因此三档缩放下的观感一致。

> 这条是本次改动里最关键的一条。缺了它，其他排版细节（缩进、字距）都救不回来。

### 3. 段落必须有印刷体特征

- 首行缩进：原文 `1.6em`，译文 `2em`（中文首行缩进两字符是惯例）
- 两端对齐（`text-align: justify`），西文开启连字符断行避免对齐后出现大片空隙
- 标题不缩进、不两端对齐、上下留白拉开
- 正文字体走衬线族：`Times New Roman` → `Songti SC` / `Noto Serif CJK SC`，贴合论文与书籍的观感
- 译文行距（1.8）比原文（1.62）松——中文需要更多行距才不挤

### 4. 保留粗体与斜体

论文章节标题里的**段首小标题**（`Identity vs. Projection Shortcuts.`）与**斜体术语**（`vs`、`bottleneck`）在纯文本化后若退化成正文，整段读起来就没有结构。因此段落模型必须携带样式片段（`TextSpan[]`），渲染时还原为 `<strong>` / `<em>`。

字重信息的来源见 `src/pdf/fontTraits.ts`：pdf.js 的 `textContent.styles` 只给归一化字体族，**没有字重**；但 `page.commonObjs.get(fontKey).name` 会给出真实 PostScript 字体名（`NimbusRomNo9L-Medi` = 粗体），据此判定。

### 5. 译文字号跟随原文

图注的字号是正文的 0.9 倍，它的译文也必须是 0.9 倍。第一版让译文一律用正文基准字号，结果图注的译文比图注本身还大，一眼就不对。标题例外：译文按正文字号排，不跟着标题放大。

## Consequences

**变得更容易：**

- 读者的阅读节奏是连续的，而不是"读一格、跳一格"
- 行宽受控后，同一段文字的行数更少（少回行），页面总高度也随之下降
- 样式片段是通用能力，后续做公式保留、代码块识别都能复用

**变得更困难 / 需要接受：**

- **行宽与图像尺寸被耦合了**。缩窄 measure 必然缩小图像，二者不能用同一套参数各调各的。若将来要"正文窄、图大"，必须让图像支持溢出容器（目前的实现是同宽）
- **样式片段必须维护字符偏移**。行内拼接、跨行拼接、行尾连字符还原都会改变偏移，任何一处漏改都会让粗体范围错位。已用单测覆盖（含连字符还原后的偏移）
- **依赖 PostScript 命名惯例**判断粗体，不是权威元数据。遇到自造字体名会退化为"常规体"，即不粗不斜——内容不会错，只是样式丢失
- 衬线字体在小字号下的可读性弱于无衬线，若将来面向小屏设备需要重新评估

**何时应当推翻此决策：**

1. 若产品定位改为"快速扫读"而非"精读"，36em 可能需要进一步收窄或改为可配置
2. 若需要"正文与图像不同宽"的版式（如通栏大图 + 窄正文），measure 方案需重做
3. 若用户明确要求译文用独立色块（例如用于批量校对场景），第 1 条应让位
