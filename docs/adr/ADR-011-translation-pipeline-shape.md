# ADR-011: 翻译流水线的实现形态

## Status

Accepted（2026-09-24）

## Context

ADR-005 定下了「翻译异步任务化 + 段落级缓存」的方向，但没有回答几个必须落地的细节：
请求是逐段发还是批量发、缓存键包含哪些字段、浏览器直连模型服务被 CORS 拦住怎么办、
API Key 存在哪里、LLM 的漏译与扩写如何处置。这些选择都会留下长期影响，
且事后修改的代价不对称（请求粒度改了要重做缓存与重试，Key 存放改了要动安全模型）。

本 ADR 只记录**这一版原型**的实际决策与理由，不追求终局。

## Decision

### 1. 一句话：逐段请求，并发 4，失败隔离，缓存前置

调度器（`src/domain/translationScheduler.ts`）从共享游标领取任务，
固定并发 worker 池；缓存命中在 worker 内前置处理，不发请求。

### 2. 逐段请求，不做批量

**放弃了什么**：批量（一次请求翻 5–10 段）能显著减少请求数，也能给模型更多上下文，
术语一致性通常更好。

**为什么仍然选逐段**：

| 关注点 | 逐段 | 批量 |
|---|---|---|
| 失败隔离 | 一段失败只影响一段 | 一段触发内容过滤，整批都得重来 |
| 增量回填 | 每段完成即可显示 | 必须等整批返回 |
| 重试粒度 | 精确到段 | 整批重试，已成功的段重复计费 |
| 输出解析 | 直接用 | 需要切分模型输出，而模型不保证格式 |
| 返回长度控制 | 不受 max_tokens 挤压 | 长批次可能被截断，后几段静默丢失 |

其中「批量输出需要切分」是最关键的排除理由：模型不保证按约定分隔符输出，
一旦切分错位，译文会**错配到别的段落**——这是比慢更严重的问题。
批量作为优化项留到后续版本，且必须先有可靠的输出切分与校验策略。

### 3. 缓存键包含 `promptVersion`

`cacheKeyOf = v1 | provider | model | targetLang | promptVersion | hashText(source)`

`promptVersion` 是最容易漏掉的一项。漏了它的后果是：改完提示词、重新翻译，
输出却毫无变化——因为命中了旧缓存。这个现象会被误判成「模型不听话」，
而真实原因在自己这边。

约定：**修改 `TRANSLATION_SYSTEM_PROMPT` 时必须同步递增 `promptVersion`**。

### 4. Vite 代理是必需项，不是可选项

```
/api/llm  →  https://api.deepseek.com
```

OpenAI 兼容的模型服务**都不给浏览器发 CORS 头**。浏览器直连会被拦，
而且报错是 `Failed to fetch`——从这条信息完全推不出是 CORS 问题，
很容易误判成网络不通或 Key 错误，白排查很久。

因此 `Provider 抽象层` 从「优雅设计」变成了硬需求：`baseUrl` 是构造参数，
开发期指向代理，迁到 Tauri 后由 Rust 侧发请求、指向真实域名。

代理 target 支持 `LLM_PROXY_TARGET` 环境变量覆盖，用于指向本地假模型服务。

### 5. API Key 暂存 localStorage —— **已知不安全，必须替换**

当前原型把 Key 存在 `localStorage`。任何能在这个 origin 上执行脚本的代码都能读到它。

之所以仍然这么做：浏览器原型没有系统钥匙串可用。
`docs/05-tech-stack.md` 定的方案是系统钥匙串（macOS Keychain / Windows Credential
Manager / libsecret），**迁到 Tauri 时必须换成那个**。

界面里把这件事直接写给用户看（而不是藏起来），并提示使用**额度受限的专用 Key**。

### 6. 译文质量校验：只做保守规则，且**告警而非拒绝**

`checkTranslationQuality` 只保留三条几乎不可能误判的规则：
输出为空、输出里没有中文字符（模型把原文抄回来了）、长度比 < 0.25 或 > 2.5。

有告警的译文**照常交付**，只是标记出来。理由：自动重译有代价，
而误判会让用户对「异常标记」整体失去信任。宁可漏报，不可虚报。

### 7. 逐段回填 + 细粒度订阅

译文逐段到达，每段完成就写入快照并通知订阅者。前端用
`useTranslationsFor(keys)` 做**按页订阅**：只有本页关心的 key 变化才返回新 Map。

若每页都订阅整个快照，翻译 150 段就是 150 次「全部已加载页重建文档流」，
而重建包含按 bbox 裁切 canvas——瀑布流会明显卡顿。

配套要求：`subscribe` 与 `getSnapshot` 必须返回稳定引用（`useSyncExternalStore` 会校验），
且 `register` 必须幂等（否则快照更新 → 重渲染 → 再登记 → 无限循环）。

### 8. 假模型服务是**验证基础设施**，不是临时脚本

`scripts/mock-llm.mjs` 提供 OpenAI 兼容接口、按输入长度生成等比例中文、
并支持故障注入（`[[429]]` `[[401]]` `[[500]]` `[[EMPTY]]` `[[SLOW]]`）。

它被集成测试直接 import、监听 0 号端口，因此测试**自带服务**、不依赖外部进程。
这让「429 是否退避重试」「Retry-After 是否被尊重」「并发上限是否被遵守」
这些用真实模型无法确定性验证的事变得可断言。

## Consequences

### 变得容易

- 换 Provider 只加一个适配器（OpenAI 兼容的一套覆盖 DeepSeek / Kimi / 通义 / Ollama）
- 调度逻辑可离线测试：用一个假 Provider 覆盖并发、重试、取消
- 全链路可离线验证：假服务 + 集成测试，无需 API Key、无外部依赖
- 重复点击翻译零成本（缓存命中），用户可以在滚动加载新页面后放心再点

### 变得困难 / 需要接受

- **请求数多**：100 段就是 100 次请求。DeepSeek 便宜所以可接受，但它不是零成本
- **段间术语一致性弱**：没有跨段上下文，同一术语在不同段可能出现不同译法。
  这属于「术语表（GlossaryService）」要解决的问题，本版未做
- **API Key 存放不安全**：必须在迁 Tauri 时替换
- **无流式**：等待期间用户只能看到进度条，看不到译文逐字出现。
  架构里预留了 Channel 流式回传，本版未用

## 何时应当推翻此决策

- 翻译成本成为主要矛盾 → 引入批量请求，但必须先有可靠的输出切分与错配校验
- 术语一致性问题突出 → 先做术语表注入，仍不够再考虑批量 + 上下文
- 段落长度普遍很短的文档（如大量短题注）→ 逐段请求的固定开销占比过高
