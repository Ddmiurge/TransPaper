# ADR-001: 采用本地优先的模块化单体，不做服务端

## Status

Accepted（2026-09-20）

## Context

本项目是一个论文阅读与管理工具，需要满足：导入 PDF（R1）、侧边栏归档管理（R2）、段落级对照翻译（R3）。

在决定架构风格前，先明确约束：

- **单用户、单机**。不存在多客户端并发访问同一份数据的需求。
- **必须离线可用**。论文常含未发表内容；用户可能在无网络环境（如飞行中、涉密环境）阅读。
- **需要直接读写本地文件系统**。导入 PDF 与 AssetStore 资源存储都依赖原生文件 IO。
- **长驻应用**。阅读器会长时间开着，待机内存敏感。
- **解析与翻译是重活**。PDF 版面分析耗时秒级到十秒级，LLM 调用需要等待网络往返。这些不能阻塞 UI 线程。

候选方案：

| 方案 | 说明 |
|---|---|
| A. 本地模块化单体 | 单进程应用，Rust 二进制承担后端，前端跑在系统 WebView；重活走任务队列 + 子进程 |
| B. 客户端 / 服务端分离 | 本地或远程跑一个 HTTP 服务，前端通过 API 访问 |
| C. 纯前端应用 | 全部逻辑跑在浏览器 / WebView，用 IndexedDB 存储 |
| D. 微服务 | 按限界上下文拆成多个可独立部署的服务 |

## Decision

**采用方案 A：本地优先的模块化单体。**

具体形态：Tauri 2 应用，Rust 编译的原生二进制承担全部后端逻辑，前端 React 运行在系统 WebView 中，两者通过 IPC 通信。重活（版面分析、翻译调度）通过**任务队列 + 子进程隔离**处理，而不是另起服务。

内部严格分层（表现层 / 应用层 / 领域层 / 基础设施层），并按五个限界上下文组织模块。

## Consequences

### 变得更容易

- **零部署成本**。用户下载即用，不需要安装数据库、不需要配置端口、不需要管理服务进程。
- **数据完全在用户手中**。整个文献库就是 `library.db` + `assets/` 两项，可复制、可备份、可迁移。对"个人长期知识积累"这类数据，用户对数据位置的掌控感是产品信任度的一部分。
- **离线能力天然完整**。核心功能不依赖网络；翻译可降级为本地 Ollama。
- **性能与延迟**。无网络往返，IPC 是进程内通信。打开一篇论文的延迟由解析与渲染决定，不受服务层影响。
- **隐私边界清晰**。默认零网络请求（除用户显式授权的翻译 Provider），安全审阅只需要审计网络出口点。

### 变得更困难 / 需要接受

- **无法多端实时同步**。这是最大的牺牲。若用户想"办公室和家里用同一个文献库"，需要靠导出 / 导入手动合并，二期才考虑 CRDT。
- **模块边界靠纪律约束，而非网络边界强制**。在微服务中，跨模块的越权调用会失败；在单体中，它只是"写起来有点别扭"。因此必须用**编译期手段**兜底：把领域层拆成独立 crate，其 `Cargo.toml` 中不声明任何 IO 依赖，让编译器执行依赖规则。
- **单点故障影响面更大**。进程崩溃会终止所有任务。缓解：解析走 sidecar 隔离（ADR-006），翻译任务状态持久化在 SQLite 中，重启后可续传。
- **未来若要做团队协作，需要重写数据层**。但产品定位已明确排除此方向（见 `01-architecture-overview.md` 非目标章节）。

### 后续可回收的选项

若某天确实需要服务端（例如协作功能），领域层与数据流可以完整保留——它们被设计为不依赖具体外壳（依赖倒置，端口在领域层定义）。届时只需替换基础设施层的适配器，并把 IPC 换成 HTTP。这是选择模块化单体而非大泥球的主要收益。
