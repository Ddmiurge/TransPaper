# ADR-005: 翻译异步任务化 + 段落级缓存

## Status

Accepted（2026-09-20）

## Context

需求 R3 的"一键翻译"涉及一次典型的规模化操作：一篇 100 页论文约 250 - 400 个 Segment。

如果按同步"请求—响应"模式实现（用户点击 → 逐段等待 → 全部完成后一次性渲染），会遇到三个问题：

1. **等待时间不可接受**。按每段 3 秒计算，即使并发 8，400 段也需要约 150 秒。用户会认为软件卡死。
2. **失败无法处理**。中途某段失败，整个操作的状态未知。
3. **重复劳动**。论文中大量内容重复（页眉页脚、方法描述复用、同一公式的多次解释），每次都重新翻译是浪费。

同时，"一键翻译"这个交互形态暗示了**用户期望立即看到反馈**，而不是等一个 loading 直到全部完成。

## Decision

**把翻译实现为异步任务流水线，粒度是 Segment。**

四个关键决策：

### 1. Segment 级别的状态机

每个 Segment 独立维护状态：`Pending → Running → Done / Failed`。失败可重试（重试次数上限 3 次，之后转人工）。

这带来两个直接好处：**断点续传**（进程崩溃后未完成的段落重启即可继续）与**部分成功可接受**（400 段中失败 3 段不影响其他 397 段的使用）。

### 2. 缓存命中前置

在派发任务**之前**先做缓存查询：

```
cacheKey = sha256(sourceHash ‖ targetLang ‖ provider ‖ model ‖ glossaryVersion)
```

命中则直接置 `Done` 并推送事件，不发起网络请求。

`glossaryVersion` 必须计入缓存键。否则用户新增术语后，旧译文会因缓存命中而不被更新——这是一个静默的错误。

### 3. 流式返回 + 内存累积 + 完成时单事务落库

- Provider 返回的 token **逐段推送给前端**（通过 Tauri 2 的 IPC Channel），用户能看到译文在"生长"，约 1-2 秒内看到第一段
- 但 token **不逐字写库**。只在内存中累积
- 段落完成后，以**单个事务**写入 Translation 与更新 Segment 状态

理由：若每个 token 都是一次数据库写入，400 段 × 平均 200 token = 8 万次写入，写队列会被打满，拖慢应用中所有其他操作。用户看到的效果完全一致，但数据库压力下降几个数量级。

### 4. 优先级：可见区优先

请求携带当前可见页范围。调度器按以下顺序派发：

1. 当前可见页的 Segment
2. 可见页之后 3 页内的 Segment（预读）
3. 其余按阅读顺序升序

这条使"一键翻译"的体验从"等全部完成"变成"立刻能读当前页"。

### 5. 术语表变更不触发全文自动重译

`glossaryVersion` 递增后，所有旧译文保留（`isActive = false`），状态重置为 `Pending`，但**不自动重新翻译**。用户在 UI 上明确选择"仅重译未完成段落"或"全文重译"。

理由：用户新增一个术语就触发 400 段重新翻译，产生的时间与费用开销不可接受。

## Consequences

### 变得更容易

- **首屏体验质变**。用户点击后 1-2 秒看到第一段译文，而不是等待 2-3 分钟。
- **失败可恢复**。单段失败不影响整体，UI 明确列出失败段落并提供重试按钮。
- **重复内容零成本**。同一段落文本在缓存命中时不需要任何网络请求。
- **成本可预测**。缓存命中率与 token 消耗都有埋点，用户可以看到"本次翻译节省了 37% 的请求"。
- **可取消**。用户随时可以取消，已完成的部分保留，正在进行的请求 abort，`Running` 回滚为 `Pending`。

### 变得更困难 / 需要接受

- **状态管理复杂度显著上升**。需要处理：部分失败、取消后的一致性、进程崩溃后的恢复、重试导致的状态竞争。这些都要靠 Segment 状态机 + SQLite 持久化来兜住。
- **缓存的正确性依赖 `sourceHash` 的精确性**。哈希的输入必须包含"文本 + 归一化规则版本"。若归一化规则改变而未更新哈希，会出现显示旧译文却不自知的问题。不变量 INV-4 强制了这一约束。
- **上下文窗口增加 token 成本**。默认前后各 1 段的上下文，约增加 30-60% 的 token 消耗，换取术语一致性的提升。此值可配置，用户可以关掉。
- **上游 Provider 成为瓶颈**。并发上限受 Provider 限流约束，用户可能觉得"怎么才 150 段/分钟"。需要 UI 上明确展示进度与预计剩余时间。

### 明确放弃的东西

- **不做流式逐字落库**。见上文第 3 点的理由。代价是进程崩溃时丢失当前正在翻译的段落（回到 `Pending` 重译），这个损失可接受。
- **不做同步翻译接口**。所有翻译都走任务队列，即使只翻一段。
- **不做自动全文重译**。见上文第 5 点。
- **不做多 Provider 混合调度**。一次翻译任务使用单一 (provider, model)，不做"简单段落用便宜模型、复杂段落用贵模型"的智能路由。这会显著增加实现复杂度，且缓存键已经按 provider/model 区分，未来要加并不困难。
