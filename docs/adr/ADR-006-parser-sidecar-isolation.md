# ADR-006: 解析器采用独立子进程隔离

## Status

Accepted（2026-09-20）· **实现偏离**：实际采用同进程 pdf.js（`app/src/pdf/pdfjsAdapter.ts`），
未引入 sidecar 子进程。偏离理由见 ADR-008/ADR-016 的演进——重排路线下
pdf.js 直读文本层已够用，sidecar（版面分析 / OCR）推迟到出现真实需求时再评估。

## Context

需求 R1 的导入环节需要从任意 PDF 中提取结构化内容。这件事的失败率**远高于普通代码路径**：

- PDF 是一种"什么都能塞进去"的格式。损坏文件、加密文件、非标准生成的 PDF 大量存在。
- 版面分析算法（双栏检测、阅读顺序重建）在遇到异常结构时容易进入病态路径——死循环、内存爆炸、栈溢出。
- 复杂 PDF 的处理可能耗时数十秒，若与主进程共享线程池会拖慢其他任务。
- 该领域（Python 的 PyMuPDF / pdfplumber / 版面分析库）生态最成熟，迭代速度远快于 Rust。但 Python 代码的崩溃（C 扩展段错误）会直接杀掉整个进程。

核心问题：**一个论文解析失败，不应该让整个应用崩溃或卡死。**

候选方案：

| 方案 | 做法 | 问题 |
|---|---|---|
| A. 纯 Rust，进程内 | 全部用 Rust 实现，跑在 tokio task 中 | 病态 PDF 会耗尽内存或 panic；Rust 的 panic 可以 catch，但 OOM 和 C 扩展段错误不能 |
| B. 纯 Python sidecar | 全部解析逻辑放 Python 子进程 | 常见论文也要付出 IPC 与 Python 启动开销；打包体积增大 |
| C. 混合：Rust 主 + Python sidecar 备 | 常见论文走 Rust，复杂版面走 sidecar | 两套解析器需统一的输出契约 |
| D. 云端解析服务 | 上传 PDF 到服务端解析 | 违背本地优先（ADR-001）；隐私不可接受 |

## Decision

**采用方案 C：混合模式，sidecar 作为隔离子进程。**

**分层策略**：

| 论文类型 | 解析路径 |
|---|---|
| 单栏、结构规整、PDFium 提取文本正常 | **Rust 内置解析器**（PDFium + 自研启发式规则） |
| 双栏/多栏、跨页表格、文本提取异常、扫描件 | **Python sidecar** |

**sidecar 的生命周期管理**：

- 按需启动，不常驻
- 空闲超时（默认 5 分钟）自动退出，释放内存
- 崩溃后自动重启，**并对当前论文降级处理**（不让用户看到崩溃）
- 单次任务超时（默认 120 秒）强制终止并判定该论文解析失败
- 并发上限 1（一篇论文同一时刻只允许一个解析任务），避免资源争抢

**输出契约**：

两种解析器必须产出**完全相同结构**的中间表示（Block 列表 + 页面信息）。契约在领域层定义，sidecar 通过标准输入输出传递 JSON（大体积二进制资源通过临时文件路径传递，不走 stdout）。

```
Rust → sidecar:  { pdf_path, options }
sidecar → Rust:  { pageCount, readingOrderConfidence, blocks: [...], assets: [...] }
```

**统一的失败信号**：sidecar 崩溃、超时、返回非零退出码、输出 JSON 解析失败——四种情况在应用层被归为同一个 `LayoutPortError`，走同一套降级路径。

## Consequences

### 变得更容易

- **故障隔离**。sidecar 段错误或 OOM 只杀死自己，主进程存活，用户看到的是"这篇论文版面识别失败，已降级"。这是本决策最核心的收益。
- **解析生态可用**。可以直接使用 Python 版面分析库，不需要在 Rust 中重新实现。
- **迭代速度快**。版面分析算法需要反复调参，Python 的迭代周期远短于 Rust。
- **可独立升级**。解析器可以独立于主程序更新，不需要重新分发整个应用。
- **超时可控**。卡死的解析可以被强制终止，这是进程内方案做不到的。

### 变得更困难 / 需要接受

- **打包体积增大**。需要携带 Python 运行时或预编译的独立可执行文件（推荐后者，如 PyInstaller / Nuitka 打包成单文件）。这是安装包从 ~3 MB 增长到 ~30-80 MB 的主要原因。
- **需要维护输出契约**。两套解析器必须产出相同结构，契约变更时需要同步修改两侧。缓解：契约在领域层定义为 Rust 类型，并生成 JSON Schema，sidecar 侧按 Schema 校验输出（含契约测试）。
- **IPC 开销**。JSON 序列化 + 进程间传输。对于一篇 3000 个 Block 的论文，JSON 约 2-5 MB，传输耗时在百毫秒级，可接受。
- **调试链路变长**。问题可能出在 Rust、IPC 或 Python 任一侧。缓解：sidecar 的日志独立落盘，并记录每次调用的输入文件哈希，便于复现。
- **跨平台打包复杂度**。需要为 Windows / macOS / Linux 各构建一份 sidecar 二进制。这是持续集成配置的额外负担。

### 明确放弃的东西

- **不做纯 Rust 解析器**作为唯一方案。理由见上表方案 A。
- **不做纯 Python 解析器**作为唯一方案。理由见上表方案 B——常见论文走 Rust 路径的延迟显著更低。
- **不做云端解析**。违背本地优先原则（ADR-001）与隐私约束。
- **不做 OCR 的独立服务**。OCR 作为 sidecar 内的一个可选能力，而不是第三个进程。理由：OCR 与版面分析耦合紧密，拆开反而增加复杂度。

### 需要注意的实现细节

**sidecar 的启动开销是真实成本。** Python 解释器冷启动约 200 - 800 ms，若加上重量的版面分析库 import，可能到 1-2 秒。因此：

- 不常驻，但**批量解析时不立即关闭**（例如用户一次拖入 10 篇论文，sidecar 全程存活）
- 冷启动耗时必须计入埋点，用于判断预编译二进制是否真的比解释器启动更快
