# 06 · 路线图与风险

## 1. 分期策略

分期的原则是：**先做最不确定的事，把确定的事推迟。**

本项目最大的不确定性不在外壳、不在界面，而在两个地方——**段落重建算法能否在真实论文上可用**，以及**覆盖式渲染能否定位准确**。这两件事决定了产品能否成立。因此它们必须最早被验证。

| 里程碑 | 目标 | 不包含 |
|---|---|---|
| **M1 · 可行性验证** | 证明段落重建与覆盖式渲染在真实论文上可用 | 不接真实 LLM、不做侧边栏、不接 Tauri |
| **M2 · 可用产品** | 完整的三条需求可用 | 不做多栏/扫描件优化、不做导出 |
| **M3 · 完整能力** | 复杂论文、术语表、导出、块改判 | 不做 RAG / 问答 |

## 2. M1 · 可行性验证

**形态**：浏览器中运行的纯前端原型（TypeScript），或 Electron 壳体。**不写 Rust**（理由见 `05-tech-stack.md` §3）。

### 交付物

| 交付物 | 说明 |
|---|---|
| `ParagraphBuilder` 实现 | 按 `02-domain-model.md` §5 的算法与签名，纯函数 |
| 黄金数据集 | 20 篇真实论文，覆盖六种形态（见 `02` §5 测试策略） |
| 回归测试 | `segmentCount` 相对基线变化 < 5% 的门禁 |
| 覆盖式渲染原型 | pdf.js + 译文文本层，支持撑开 / 折叠 / 浮层三种模式 |
| 定位准确率报告 | 人工标注 300 个段落的译文位置，统计正确率 |

### 验收标准（Go / No-Go）

| 指标 | 门槛 | 不达标怎么办 |
|---|---|---|
| 段落重建的 `segmentCount` 偏差 | 六种文档形态各自 < 15% | 调整算法参数；若双栏场景 > 30%，考虑提前引入 sidecar 版面分析 |
| 覆盖式渲染定位准确率 | ≥ 80% | 若低于 70%，需要重新评估 ADR-003——把重排模式提为默认 |
| 跨页段落腰斩率 | < 5% | 调整 `crossPageGapTolerance` 判定逻辑 |
| 100 页论文重建耗时 | < 500 ms | 若非纯循环实现问题，考虑增量重建 |

> **这是一个真正的 Go / No-Go 关卡。** 如果覆盖式渲染的定位准确率达不到 80%，整个 R3 的实现方案需要重做——不是调参，而是换方案。不要跳过这一关直接做 M2。

### 明确不做的事

- 不接真实 LLM。用固定返回的假 Provider 验证调度逻辑与渲染。
- 不做文献库持久化。用内存状态即可。
- 不做块类型分类器。手工标注块类型，先验证重建与渲染。
- 不接 Tauri。

## 3. M2 · 可用产品

**形态**：Tauri 2 应用，完整数据持久化。

### 交付范围

| 需求 | 范围 |
|---|---|
| **R1 导入** | 指纹去重、PDFium 提取、**单栏论文**的阅读顺序重建、元数据抽取（DOI / arXiv 优先，失败降级） |
| **R2 侧边栏** | 集合树（可嵌套）、标签、智能集合、全文检索（FTS5 + trigram）、拖拽归入、阅读进度 |
| **R3 翻译** | Segment 状态机、异步调度、缓存、流式增量渲染、三种显示模式、失败重试、Provider 抽象（至少接一个云端 + 一个本地） |

### 基础设施交付

- SQLite Schema 与迁移机制（`04-storage-design.md` 完整 DDL）
- 单写者写队列
- AssetStore（内容共享 + 垃圾回收）
- 系统钥匙串集成
- 事件流与 `EventBridge`
- 日志与埋点（至少覆盖 `01` §9 列出的位置）

### 验收标准

| 指标 | 门槛 |
|---|---|
| 100 页单栏论文解析完成 | < 10 秒（M 系列芯片） |
| 点击翻译后首段译文出现 | < 2 秒 |
| 待机内存 | < 150 MB |
| 打开 100 页论文的峰值内存 | < 500 MB |
| 翻译中断后重启 | 未完成段落可续传 |
| 默认状态下的网络请求 | 零（除用户显式授权的翻译 Provider） |
| 领域层测试覆盖率 | > 80%，且不依赖数据库 |

### 明确不做的事

- 不做双栏 / 多栏论文（走降级路径）
- 不做扫描件 OCR
- 不做块类型手动改判（M2 阶段接受分类错误，用户可通过重排模式规避）
- 不做导出
- 不做术语表

> **M2 的关键取舍**：先把单栏论文做扎实。双栏是学术论文的主流，因此这个限制必须在 UI 上明确告知，而不是让用户自己发现译文错位。

## 4. M3 · 完整能力

| 交付项 | 说明 | 依赖 |
|---|---|---|
| 双栏 / 多栏支持 | sidecar 版面分析（ADR-006） | M2 的 `LayoutPort` 已就绪 |
| 块类型手动改判 | 右键改判 + `override_anchor` 持久化（ADR-004） | `04` §4.4 的表已建 |
| 术语表 | 含版本管理与缓存失效联动 | ADR-005 |
| 扫描件 OCR | 走 sidecar | ADR-006 |
| 导出 | 双语 Markdown / HTML | 覆盖式渲染无法导出 PDF，见 ADR-003 |
| 阅读库导出 / 导入 | 应对"不可放网盘同步"的限制 | ADR-007 |
| 向量检索与问答 | `sqlite-vec`，在同一库内 | 非 R1-R3 需求，属扩展 |

## 5. 风险登记册

按「影响 × 可能性」排序。

| # | 风险 | 影响 | 可能性 | 缓解措施 | 触发信号 |
|---|---|---|---|---|---|
| R-01 | **覆盖式渲染定位不准** | 致命——R3 的核心体验崩塌 | 中 | M1 阶段用真实论文验证，设 80% 门槛 | M1 准确率报告 < 80% |
| R-02 | **双栏论文阅读顺序错乱** | 高——译文大面积错位，用户失去信任 | 高 | 先用单栏限定范围；M3 引入 sidecar 版面分析；`readingOrderConfidence` 低时主动提示 | 埋点中双栏文档的置信度分布 |
| R-03 | **块类型分类器误判**（表格→正文、公式→图片） | 中——破坏 R3 的"保持原样" | 高 | ADR-004 的用户改判入口（M3）；M2 阶段靠重排模式规避 | 用户改判频率、分类置信度分布 |
| R-04 | **译文比原文长撑破版式** | 中——可读性下降 | 中 | 三种显示模式；页内撑开不跨页推挤 | 译文/原文长度比统计 |
| R-05 | **中文 FTS5 检索效果差** | 中——侧边栏搜索不可用 | 中 | 使用 `trigram` tokenizer；M2 阶段用真实中文语料验证 | 搜索结果相关性抽查 |
| R-06 | **sidecar 打包与跨平台构建复杂** | 中——拖慢交付 | 中 | 推迟到 M3；M2 只用 Rust 内置解析器 | CI 构建失败率 |
| R-07 | **Rust 学习成本超出预期** | 中——进度延期 | 中 | `05` §3 的渐进路径：M1 不写 Rust | M1 阶段的实际投入 |
| R-08 | **LLM 漏译 / 自行扩写 / 幻觉** | 中——内容失真，学术场景不可接受 | 中 | 段落级校验：长度比异常、数字不一致的段落标红可重译 | 人工抽查 |
| R-09 | **用户把库文件放网盘导致损坏** | 高——数据丢失 | 中 | UI 明确警告；提供库导出 / 导入 | 崩溃报告中的 SQLite 错误码 |
| R-10 | **Provider 限流导致翻译极慢** | 中——体验差 | 中 | UI 展示进度与预计剩余时间；支持本地 Provider | 429 频率埋点 |
| R-11 | **三平台 WebView 渲染差异** | 中——特定平台 UI 破损 | 中 | 前端保持保守；**从 M2 第一周开始三平台测试** | 各平台回归测试 |
| R-12 | **段落重建在修一个 case 时破坏另一个** | 中——回归 | 高 | 黄金数据集 + 5% 变化门禁 | 回归测试失败 |

### 需要尽早验证的 Spike（技术预研）

按优先级排序，**每个 spike 的时间盒都应设上限，到点即做决策**：

| 优先级 | Spike 内容 | 要回答的问题 |
|---|---|---|
| P0 | pdf.js 文本层坐标 ↔ 自定义译文层的对齐 | 缩放、滚动、DPI 变化下能否保持像素级对齐？这是 R-01 的技术前提 |
| P0 | `ParagraphBuilder` 在 20 篇真实论文上的表现 | 算法是否需要引入更重的版面分析？ |
| P1 | FTS5 `trigram` 在中文论文上的检索质量与索引体积 | 索引体积是否可接受？搜索结果是否可用？ |
| P1 | 一篇 100 页论文的 Block 数实测与 SQLite 写入耗时 | 百万行量级的索引设计是否需要调整？ |
| P2 | Python sidecar 的冷启动耗时与打包体积 | 是否值得？预编译二进制 vs 解释器启动 |
| P2 | Tauri 2 Channel 的流式 IPC 实测吞吐 | 逐 token 推送是否会造成 IPC 拥塞？ |

## 6. 开工建议

**第一步不是搭建项目骨架，而是做 P0 的两个 spike。**

项目骨架（Tauri 工程、目录结构、CI）是确定性工作，什么时候做都能做对。而 P0 spike 的结论会决定架构是否需要修改——如果覆盖式渲染不可行（R-01），那么 `02` 的领域模型仍然成立，但 `03` 的渲染数据流与 `05` 的技术选型都要重写。

先把不确定性最大的东西验证掉，再动手搭架子。这也是 `05-tech-stack.md` §3「渐进式引入 Rust」的同一个逻辑——**推迟确定的工作，前置不确定的工作**。
